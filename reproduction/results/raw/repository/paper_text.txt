They help identify potential bugs early in the development process by scanning the codebase without extensive program execution Cai et al. (2023) ; Cai et al. (2022) ; Cai et al. (2021) ; Shi et al. (2020) ; Shi et al. (2018) ; Sui et al. (2012) ; Vassallo et al. (2020) ; Yan et al. (2018) . Popular analyzers like GitHub CodeQL cod (2025) , Facebook Infer inf (2025) , and CppCheck cpp (2024) are widely used for industrial bug detection. Their analysis of many bug types (e.g., null pointer dereference and use-after-free) typically follows a standardized approach: identifying sources (i.e., potential origins of issues) and sinks (i.e., locations where issues manifest) based on predefined rules, then checking whether a feasible execution path exists from sources to sinks. If such a path is found, the tools flag a potential bug. However, in complex software systems, sources and sinks often reside in different functions. In cases where function call chains between a source and a sink are lengthy and involve multiple conditional branches and complex data dependencies, traditional static analyzers struggle to comprehensively validate path feasibility between sources and sinks, resulting in high false positive rates. For instance, our manual annotation of sampled bug reports reveals that popular tools produce an extremely high rate (e.g., over 90%) of false positives for use-after-free bugs across large-scale software such as Linux Kernel. This significantly burdens developers due to the large efforts in manually reviewing the false alarms reported by these tools. Existing Techniques. As Large Language Models (LLMs) are increasingly applied to code-related tasks Du et al. (2024a) ; Liu et al. (2024) ; Nam et al. (2024) ; Du et al. (2024b) , researchers have leveraged their advanced program understanding capabilities to reduce false positives generated by static analyzers. However, existing LLM-based approaches have limited effectiveness in handling path feasibility analysis within large, dependency-rich codebases. Specifically, LLM4SA Wen et al. (2024) feeds entire source-to-sink call chains along with bug reports into LLMs at once to identify false positives, without conducting fine-grained constraint analysis and relying entirely on the LLM’s ability to assess complex path feasibility. LLMDFA Wang et al. (2024a) performs data flow analysis for each function along all potential execution paths between sources and sinks, which results in significant time and computational cost when applied to large-scale projects with complex call dependencies. While symbolic execution can perform path feasibility analysis, it suffers from path explosion when traversing all possible paths, particularly when dealing with multiple conditional branches, loops, nested function invocations, or compound data types Baldoni et al. (2018) . Therefore, it cannot scale to large and complex software systems in practice. Our approach. To address these limitations, we propose LLM4PFA , an LLM-powered path feasibility analysis framework designed to minimize false positives in static bug detection for complex software projects. Specifically, Given a function call trace and a target variable with its source and sink, LLM4PFA iteratively performs two-phase analysis for each function: (1) Feasibility Constraints Extraction first identifies critical conditional expressions impacting sink reachability; then employs LLM agents to conduct symbolic range reasoning for variables and function calls within each expression. (2) Constraints Solving employs constraint solver to iteratively solve the SMT query scripts generated by LLM. Overall, LLM4PFA offers the following advantages compared to traditional symbolic execution and existing LLM-based methods: • Precise complex constraint cascade analysis. Breaking down inter-procedural feasibility analysis into localized symbolic range reasoning, LLM4PFA amplifies LLMs’ program comprehension strength on focused code segments Li et al. (2023b) , thereby significantly enhancing reasoning effectiveness. • Efficient complex context analysis. Integrating prioritized feasible path constraints extraction method with agent-guided planning, LLM4PFA effectively mitigates path explosion in sequentially traversing deeply-nested contextual functions. Evaluation. We manually construct a new dataset, SAFP-BENCH-C, for a more realistic evaluation, which takes approximately 100 person-hours. It contains 364 warnings generated by three advanced static analyzers, covering three important bug types (i.e., null pointer dereference, buffer overflow, and use after free) in large-scale software projects, including the Linux Kernel (with over 18 million lines of code), OpenSSL (with over 300K lines of code), and Libav (with over 600K lines of code). Our evaluation shows that LLM4PFA precisely filters out 72% to 96%) false positives reported during static bug detection, significantly outperforming all the baselines by 41.1% - 105.7% improvements; meanwhile LLM4PFA only misses 3 real bugs of 45 true positives. Furthermore, LLM4PFA shows consistent effectiveness across four state-of-the-art LLMs, indicating the generalizability of our approach. Ablation studies further reveal that LLM4PFA outperforms two ablation variants, underscoring the key contribution of LLM agent based self-planning context analysis and iterative constraint solving proposed in our framework. This paper makes the following contributions: • A novel technique that effectively enhances complex inter-procedural feasibility analysis to minimize false positives in bug detection. • A new dataset designed for a more realistic evaluation of false positive reduction, with approximately 100 person-hours dedicated to manual construction. • An extensive evaluation demonstrating the effectiveness of LLM4PFA in filtering out false positives and identifying real bugs. (a) Complex Constraint Cascades (b) Complex Constraint-Related Contextual Analysis Figure 1: Motivating Examples 2 Preliminaries & Motivation This section introduces key preliminaries of static bug detection and presents motivating examples to illustrate the false positive issues related to path feasibility validation. 2.1 Static Bug Detection Many bugs, such as Null Pointer Dereference (NPD) and Use After Free (UAF), follow a common pattern where a target variable feasibly flows from a source (where a potential issue originates) to a sink (where the issue manifests). Source and Sink Identification. The specific definitions of the target variable, source, and sink vary by bug type. For instance, in NPD (Null Pointer Dereference) bugs, the target variable is a pointer (e.g., tun_info in Figure 1(a) ), the source is the code expression that defines or assigns it as NULL (e.g., Line 4 in Figure 1(a) ), and the sink is the code expression that dereferences the pointer (e.g., Line 105 in Figure 1(a) ). For a specific bug type b ​ t bt , given a code project 𝒫 \mathcal{P} consisting of multiple code files and lines, the identification of the sources and sinks associated with the target variables can typically be formalized through the procedures: FindSource b ​ t : Σ 𝒫 → Σ v ​ a ​ r × Σ e ​ x ​ p ​ r \textsc{FindSource}^{bt}:\Sigma_{\mathcal{P}}\to\Sigma_{var}\times\Sigma_{expr} FindSink b ​ t : Σ 𝒫 → Σ v ​ a ​ r × Σ e ​ x ​ p ​ r , \textsc{FindSink}^{bt}:\Sigma_{\mathcal{P}}\to\Sigma_{var}\times\Sigma_{expr}, where Σ ( ∗ ) \Sigma_{(*)} represents the domain of ( ∗ ) (*) , i.e., Σ v ​ a ​ r \Sigma_{var} and Σ e ​ x ​ p ​ r \Sigma_{expr} denote the complete value domains of variables and code expressions, respectively. Each s ​ o ​ u ​ r ​ c ​ e source or s ​ i ​ n ​ k sink is represented as a pair ( v ​ a ​ r , e ​ x ​ p ​ r ) (var,expr) , consisting of a target variable v ​ a ​ r var and its corresponding code expression e ​ x ​ p ​ r expr . Data Flow Analysis. For each source-sink pair ( s ​ o ​ u ​ r ​ c ​ e , s ​ i ​ n ​ k ) (source,sink) sharing the same target variable v ​ a ​ r var , data flow analysis aims to determine whether v ​ a ​ r var can flow from s ​ o ​ u ​ r ​ c ​ e source to s ​ i ​ n ​ k sink . If true, a corresponding bug is reported. For instance, in Figure 1(a) , data flow analysis for the pointer tun_info is performed between Line 4 (source) and Line 105 (sink). If a feasible execution path is found, an NPD bug is reported at the sink. This analysis can be formalized as the procedure: TraceFlow : Σ s ​ o ​ u ​ r ​ c ​ e × Σ s ​ i ​ n ​ k → { TRUE , FALSE } , \textsc{TraceFlow}:\Sigma_{source}\times\Sigma_{sink}\to\{\textit{TRUE},\textit{FALSE}\}, which returns TRUE if any feasible execution path exists between s ​ o ​ u ​ r ​ c ​ e source and s ​ i ​ n ​ k sink , and FALSE otherwise. Path Feasibility Validation. Performing precise data flow analysis is challenging due to the complexity of validating path feasibility. Sources and sinks often reside in different functions, necessitating inter-procedural analysis to trace all potential execution paths. When the function call chain between a source and a sink is lengthy and includes multiple conditional branches, nested function invocations, or compound data types, the complexity of path feasibility validation increases exponentially (We will illustrate the challenges with examples in Section 2.2 ). However, traditional static analysis tools like CodeQL and Infer often incorporate over-approximation during contextual analysis, so as to reduce the complexity of path feasibility validation. As a result, there are high false positive rates in their reported bug alarms in practice. 2.2 Motivating Examples We present two examples to further illustrate the challenges of validating path feasibility, which lead to false positives in the NPD bug reported by CodeQL on the Linux kernel. Challenge-1: Complex Constraint Cascades in Path Tracing. Figure 1(a) presents a false positive reported by CodeQL. In this example, the green-highlighted sections involve value assignments and constraint validation for the two bool variables connected and md . According to the constraint in Line 34, we can deduce that only when the target pointer tun_info is not NULL , both connected and md are TRUE (Lines 36 and 37). Based on the constraint in Line 102, only if both connected and md are TRUE , can the dereference operation (the sink) at Line 105 potentially be executed. According to both constraints, it is clear that no feasible path exists to reach the sink, and thus no NPD occurs. Beyond these green-highlighted sections, the example also involves numerous preceding and succeeding conditional constraints (highlighted in orange). Only by comprehensively cascading these constraints and analyzing the potential execution paths, can accurate path feasibility validation be achieved and false positives be eliminated. Such a high complexity is prevalent in real-world software systems, which often involve intricate function call chains and deeply nested conditional structures, making path feasibility analysis even challenging. Challenge-2: Contextual Analysis. In addition to the source-to-sink function call trace, precise path feasibility analysis requires reasoning numerous variable values and function call return values, further complicating the analysis process. Figure 1(b) illustrates a false positive resulting from complex contextual analysis. In Line 3 of the second function in the trace, consume_skb correctly performs a null check on the target pointer skb by invoking skb_unref , which returns false when skb is null. This causes the program to return early, preventing the null pointer from propagating to the sink. Notably, Figure 1(b) only reveals the minimal contextual information (highlighted in green) necessary for the manual inspection to identify the false positive. Existing LLM-based approaches would consider a broader set of contextual function calls (highlighted in orange), significantly increasing the complexity of context-sensitive analysis. Furthermore, due to the intricacies of the Linux kernel, this analysis incorporates not only function calls but also macro definitions and built-in GCC compiler functions, presenting additional challenges for traditional symbolic execution techniques. Figure 2: Overview of LLM4PFA 3 Approach 3.1 Overview In this work, we present an iterative path feasibility validation framework LLM4PFA to enhance complex inter-procedural feasibility analysis for minimizing false positives in static bug detection. Figure 2 shows the overview of our approach. Given a target variable, its source and sink, and the function call trace from source to sink, LLM4PFA performs iterative feasibility analysis function-by-function. Each function is analyzed iteratively by collecting feasible path constraints and solving them to determine whether a feasible source-to-sink path exists. The process returns True if any feasible path exists, and False otherwise. This iterative process continues until either the analysis of all functions in the call trace is complete, or a False result is encountered. The detailed iterative analysis within each function proceeds as follows: • Feasibility Constraints Extraction (Section 3.2 ) : Based on the Control-Flow Graph (CFG), LLM4PFA first identifies the critical path conditional branches between source and sink, and summarizes feasible path conditional expressions. Subsequently, LLM4PFA incorporates LLM agents to conduct symbolic range reasoning for variables and function calls within each expression individually. • Constraints Solving (Section 3.3 ) : LLM4PFA leverages LLM to convert all extracted feasible path constraints into SMT query scripts, and invokes the constraint solver (i.e., Z3) for constraint solving. 3.2 Feasibility Constraints Extraction Given a function f f with the CFG entry point S f S_{f}{} and the exit point T f T_{f}{} , LLM4PFA first extracts the feasible path constraints from S f S_{f}{} to T f T_{f}{} . To improve precision and avoid the inefficiency of exhaustively traversing all possible paths, we begin by extracting a set of critical path conditional expressions that directly impact the reachability of T f T_{f} (Section 3.2.1 ). Subsequently, LLM agent reasoning is employed to determine the symbolic ranges of variables and function call return values within these expressions (Section 3.2.2 ). These conditional expressions and symbolic ranges collectively form the feasible path constraints. 3.2.1 Critical Path Conditional Expression Extraction Based on the extracted CFG of f f , LLM4PFA first identifies the critical path conditional branches, which are a set of conditional statement nodes (i.e., branching and loop constructs) that directly impact the reachability of T f T_{f} at the control flow level. These branches are represented as: N c ​ s ​ ( S f , T f ) = N e ​ ( T f ) ∪ N jump ​ ( S f , T f ) N_{cs}(S_{f},T_{f}){}=N_{\text{e}}(T_{f}){}\cup N_{\text{jump}}(S_{f},T_{f}){} where N e ​ ( T f ) N_{\text{e}}(T_{f}){} represents all conditional statement nodes nested outside the basic block containing T f T_{f}{} ; and N jump ​ ( S f , T f ) N_{\text{jump}}(S_{f},T_{f}){} refers to conditional statement nodes nested outside any basic block containing Jump/Return statements encountered between S f S_{f}{} and T f T_{f}{} . For branching statements, we focus on If statements (i.e., if , else , else if and switch ); for Loop statements, we focus on while and for statements. Regarding Jump/Return statements, we consider all goto and return statements, as well as break and continue statements within loop constructs that are nested outside T f T_{f}{} . Based on these critical path conditional branches, LLM4PFA further extracts the feasible path conditional expressions, which are represented as: F ​ P ​ E ​ ( S f , T f ) = { e ​ x ​ p ​ r f ∣ e ​ x ​ p ​ r f ∈ N e ​ ( T f ) } FPE(S_{f},T_{f}){}=\left\{expr_{f}\mid expr_{f}\in N_{\text{e}}(T_{f}){}\right\} ∪ { ¬ e ​ x ​ p ​ r i ​ f ∣ e ​ x ​ p ​ r i ​ f ∈ N jump ​ ( S f , T f ) } \quad\cup\left\{\neg expr_{if}\mid expr_{if}\in N_{\text{jump}}(S_{f},T_{f}){}\right\} Where a feasible path exists only when all e ​ x ​ p ​ r f expr_{f} are satisfied (i.e., the conditions for reaching the exit point branch are fulfilled), and none of e ​ x ​ p ​ r i ​ f expr_{if} is fully satisfied (i.e., there is no early jump to other branches). 3.2.2 Context-Aware Symbolic Range Reasoning In this step, LLM4PFA utilizes LLM agents to reason all symbolic ranges Σ v \Sigma_{v} of each feasible path conditional expression one by one. Notably, Σ v \Sigma_{v}{} encompasses the symbolic ranges from both variables and the function call return values in conditional expressions. These constraint-related function calls are not part of the input function call trace, and thus require additional contextual analysis. Variable Symbolic Range Reasoning. For each variable v v in a conditional expression, LLM4PFA reasons the possible symbolic ranges Σ v ​ ( P ) \Sigma_{v}(P){} of v v when the conditional statement is executed. In this context, P P denotes the required initial states of the program. The initial states P P are the post-conditions following the execution of S f S_{f}{} . These conditions encompass both the pre-conditions required by S f S_{f}{} and the post-conditions of the S f S_{f}{} statement. For the initial function in the input trace, P P serves directly as the post-condition of S f S_{f}{} . For subsequent functions, P P further incorporates all feasible path constraints associated with parameters passed to the current function, as extracted from the preceding function. This ensures the propagation of constraints through function call trace, enhancing the rigor of inter-procedural analysis. The definition of P P is adapted based on the specific bug type. In the case of NPD detection, the NULL state of the target pointer is propagated as P P throughout the entire function call trace analysis. Inspired by chain-of-thought (CoT), LLM4PFA directs the LLM agent to perform a step-by-step simulated execution of function code, enabling more precise reasoning by LLM. Furthermore, example analyses are included within the prompt to facilitate few-shot learning for LLM agents. The detailed prompt design is in Appendix C . Iterative constraint-related function call Symbolic range reasoning. For constraint-related function calls f ​ c fc within a conditional expression, LLM4PFA aims to determine the symbolic range Σ f ​ ( P ) \Sigma_{f}(P) of the function return value under the required initial states P P . The definitions of P P align with Σ v ​ ( P ) \Sigma_{v}(P){} . Figure 3 illustrates the framework for reasoning symbolic ranges of constraint-related function call return values. This reasoning process may require deep multi-layered contextual function analysis. To address the challenges posed by the complexity of context analysis (Challenge-2), we propose an LLM agent-based framework that leverages the tool-usage and self-planning capabilities of LLM agents for precise context analysis iteratively. Figure 3: LLM Agent-based Context-aware Return Value Range Analysis of Function Calls Given that feasible path conditional expressions may involve multiple function calls, only those with parameters relevant to P P are selected for symbolic range reasoning. For each contextual function under analysis, LLM4PFA retrieves its function body from the source code repository using a function retrieval tool. This function body, along with the initial states P P , is then provided to LLMs for reasoning. During the reasoning process, the LLM agent dynamically determines whether additional deeper contextual functions are needed to refine the analysis, leveraging its self-planning capabilities . Contextual functions that are identified as affecting the return values are further analyzed with the same process. This iteration continues until the LLM agent finalizes the result or reaches the predefined maximum iteration limit (5 in this work). To minimize resource consumption due to redundant analyses of identical function calls, we introduce a memory module. This module stores the return value symbolic range of previously analyzed function calls under distinct P P . In subsequent analyses, results for identical scenarios can be retrieved directly from the memory module. 3.3 Constraints Solving Given the feasible path constraints for T f T_{f}{} , LLM4PFA iteratively employs LLM to convert them into SMT query scripts, and invokes Z3 solver for constraint solving. Figure 4: SMT Query Script Generation When analyzing complex functions, LLM4PFA may solve numerous feasible path constraints. Directly converting all constraints into SMT query scripts at once can overwhelm the LLM. To address this, we propose an iterative generation strategy. Figure 4 illustrates this generation process, which consists of three key steps: • Script template generation. We utilize LLM to generate a Python template of the SMT query script, including imported packages and constraint solver definitions. • SMT constraints generation. With few-shot examples, LLMs then convert path constraints into SMT constraints (i.e., z3.add() format). • Script merging. Lastly, LLMs merge SMT constraints with the template to create the final script, ensuring consistency between SMT variable definitions and SMT constraints. After generating the initial script (Script 1 in Fig 4 ), the first round of constraint solving is performed. If the solver returns an UNSAT (i.e., infeasible) result, further symbolic range reasoning is terminated. During this process, each set of symbolic ranges in conditional expressions inferred by the LLM will be converted into SMT constraints and immediately merged into the script for constraint solving. Once the solver returns UNSAT , further reasoning is halted to avoid inefficient analysis of additional constraints. To address script generation errors, LLM4PFA incorporates error messages from the Z3 solver into the prompt, enabling targeted fixes by the LLM. This process repeats until the Z3 solver successfully resolves the constraints or the maximum number of fix attempts (3 rounds in our setting) is reached. The detailed prompt design of SMT query script generation is in Appendix C . 4 Evaluation 4.1 Dataset We first manually label and construct a new benchmark SAFP-Bench-C , which includes false positive reported by state-of-the-art static analyzers on real-world complex software systems. Bug Types. We target three representative categories of critical bugs: null pointer dereference (NPD), use-after-free (UAF), and buffer overflow (BOF). Target Projects. We select the latest versions of three well-maintained and large-scale C/C++ open-source projects for scanning, including the Linux kernel ker (2025) , OpenSSL ope (2025) , and Libav lib (2025) . Static Analyzers. We use three state-of-the-art static analyzers: CodeQL cod (2025) , Infer inf (2025) , and CppCheck cpp (2024) . We adopt the following sampling strategy for manual inspection: if a static analyzer detects more than 100 warnings in a project, we randomly sample 100 instances; otherwise, all instances are included. For each warning, two participants will individually label it as True or False. In total, the construction process takes around 100 person-hours. The final benchmark SAFP-Bench-C contains 364 warnings, of which 45 are real bugs. Overall, LLM4PFA demonstrates a significant superiority over NoContext and BatchSol in false positive elimination, showing 136.7% - 173.1% improvements in FPR_R. While BatchSol achieves a recall of 0.95, compared to LLM4PFA ’s 0.90 in Linux kernel vulnerability detection, this discrepancy arises from a real bug being misclassified as a false alarm by LLM4PFA due to inaccurate extraction of critical path conditional expressions. This case is still considered a bug alarm in BatchSol due to a constraint solving failure. A high rate of constraint solving failures in BatchSol contributes to its low FPR_R (0.38, 57.8% less than LLM4PFA ). Currently, substantial efforts have been made to combine LLMs with static analysis to enhance detection capabilities. Li et al. Li et al. (2023a) propose a framework that integrates UBITect with LLMs to detect Use-Before-Initialization (UBI) bugs in the Linux kernel; Sun et al. Sun et al. (2023) employ LLMs to assist static analysis in identifying logic vulnerabilities in smart contracts. Li et al. Li et al. (2024) propose IRIS, which systematically combines LLMs with the static analysis tool CodeQL to conduct the first whole-repository reasoning approach for comprehensive vulnerability detection. Wen et al. Wen et al. (2024) present LLM4SA, which utilizes LLMs to process bug warning reports from various static analysis tools, leveraging domain knowledge of LLMs to reduce false positives. Wang et al. Wang et al. (2023) propose InferROI, which employs LLMs to infer resource-oriented intentions (e.g., acquisition, release, and reachability validation) in code, combined with a two-stage static analysis approach to inspect control-flow paths for potential resource leak detection. LLMs for Program Analysis. Shahandashti et al. Shahandashti et al. (2024) investigate the application of LLMs in both static and dynamic program slicing, utilizing advanced prompting techniques such as few-shot learning and chain-of-thought reasoning. Wang et al. Wang et al. (2024a) introduce LLMDFA, the first LLM-powered dataflow analysis framework, which decomposes the problem into three components: source/sink extraction, dataflow summarization, and path feasibility validation. Subsequently, they further propose LLMSAN Wang et al. (2024b) , which leverages few-shot chain-of-thought prompting to guide LLMs in emitting data-flow paths, with validation performed through program-property decomposition. To the best of our knowledge, no prior studies have performed the iterative decomposition of complex program analysis tasks or fine-grained symbolic range reasoning. Moreover, our approach utilizes the self-planning capabilities of LLM agents to automate the iterative analysis of deeply nested functions. This effectively mitigates the path explosion problem inherent in complex inter-procedural path feasibility analysis, which existing studies have struggled to address efficiently. 6 Conclusion This paper proposes LLM4PFA , an iterative path feasibility analysis framework powered by LLM agents, which effectively enhances complex inter-procedural feasibility analysis for minimizing false positives in bug detection.
