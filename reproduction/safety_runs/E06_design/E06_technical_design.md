# E06 技术方案（提案，尚未实现）

本设计是复现适配层方案，不是作者已公开的完整算法。目标是可追溯地验证受限传播关系，任何不支持的关系不进入自动过滤。当前不改变原 Prompt、U01/U02/U06/U10、MCP、engine 或 E01–E05。

## 1. 技术路线比较

| 方案 | 主要解决什么 | 复杂度与 C 支持 | 编译环境 | 对现有架构/Prompt 的影响 | 源码追溯与局限 |
| --- | --- | --- | --- | --- | --- |
| 文本/token 序号映射 | 找调用文本与实参位置 | 低；只适合候选定位 | 不必完整构建 | 现有 context 已有；可继续作检索线索 | 无法证明 DeclRef/类型/直接被调方，不作为语义批准依据 |
| AST 的调用/声明映射 | 将 CallExpr、DeclRef、ParmDecl、转换与类型绑定 | 中；真实宏/typedef 依赖完整解析 | 自包含合成片段不需项目构建；真实项目需正确 TU/头文件/flags | 建独立证据前端，首轮不改 Prompt/主流程 | 可保留 spelling/expansion 位置；parse 有错误时不能把 recovery AST 当已验证语义 |
| 简化 SSA/变量版本 | 区分赋值前后值、复制后独立更新 | 中；限定无环、简单赋值/分支 | 依赖可靠 AST/基本控制边 | 新增 sidecar 状态层，不替代原 U02/U06 | 每个版本保留定义/使用边；不是完整 SSA，不自动解决指针内存、循环 phi 或别名 |
| 小范围调用图/调用栈 | 连接已验证直接边，区别调用上下文 | 中；初期只处理明确直接调用 | 从可靠声明和调用解析建立 | 复用已有检索，保存独立调用边账本 | 图只表示“可能调用”，不能独自证明参数值、效果或可达性；不扫描全项目 |
| 路径条件传播 | 按上下文保留 caller/callee 条件、提前退出和不同路径 | 中高；限无环、预算内分支 | 需正确控制边和状态绑定 | 最后增独立传播 IR/检查门，不先改 Prompt | 可按条件来源追溯；路径爆炸、漏路径或错误合取是主要风险 |
| Clang/libclang 辅助 | 可靠的声明/类型/隐式转换/预处理来源 | 前端工作中等；恢复真实构建成本可能高 | 对真实代码需要对应版本环境；单装工具不够 | 可复用现有 libclang 18.1.1，不能误称当前文本入口已采用这些能力 | AST 不是 points-to/效果分析，也不自动提供可直接使用的完整 CFG/SSA；libclang Python API 不等于所有 Clang C++ CFG 功能 |
| 完整 LLVM/指针分析/通用符号执行 | 广泛内存/控制流建模 | 高，远超简单复现范围 | 基本要求完整构建，源码映射也更复杂 | 大改动；本轮不推荐 | 本阶段明确不走此路线 |

这些方案互补：推荐“可靠 AST 声明与调用证据 + 受限变量版本 + 小调用上下文 + 最后路径组合”，不把调用图或更多 LLM 文本当成状态传播器。

## 2. 是否需要 SSA、是否需要 Clang

**需要显式变量版本机制，但不需要先实现完整 SSA。** 第一轮仅有 entry/callsite 身份，第二轮才加入已支持赋值的 def-use 版本。初期遇到不同分支保持不同环境，不强做 phi；遇到循环/递归/无法识别的写入返回 UNKNOWN。将来要合流，必须使用带路径守卫的选择关系，不能任取某个 reaching definition。

**推荐使用已有 libclang 做类型/声明前端，但它不是所有正向实验的外部构建前提。** 自包含、无宏、原始源码已足够的合成 C TU 可以先验证基础设计。真实项目只有函数片段时，必须检查解析诊断和缺失声明，不能自动添加 typedef、宏、头文件或默认类型后宣称原源码解析成功。没有原始构建证据的历史案例仍可得到局部诊断/缺口报告，不能得到完整传播证明。

当前包存在性和 PATH 检查仅是环境元数据；没有在本阶段启动 Clang 或加载/解析测试。是否可用及解析正确性，是未来第一轮先行门槛。若 AST 不足以导出可靠控制关系，先限制到直线语句/单一简单早退，不扩展成新的通用 CFG 分析器。

## 3. 首先统一三个不同的“身份”

| 对象 | 建议标识字段 | 不能混淆的关系 |
| --- | --- | --- |
| 源码存储单元 slot | dataset/version、TU/build digest、函数声明/链接身份、词法 scope、decl offset、类型、body hash | caller 的 p 与 callee 的 item 是不同局部 slot |
| 执行点上的值 version | slot_id、call_context_id、path_id、definition/event_id、版本号 | 同一 p 赋值前后的值不同；相同名字不等于同一版本 |
| 内存对象/位置 region | 分配/存储来源、生命周期、字段声明路径、memory version、别名证据 | 两个指针值相同不代表两个局部 slot 相同；p、*p、p->field 不能合成一个符号 |

标识必须携带来源，不只做名称拼接。Clang USR/DeclRef 可辅助，但仍要绑定 TU、版本、链接和调用上下文，不能把跨文件相同名字/不同 static 定义合并。历史缺 TU/build 身份时标记 scope 为 saved-source-only，并保留缺口，不伪造原扫描身份。

参数按值传递只建立“caller 当前实参值经过合法转换后，等于 callee 入口形参值”的关系。它不会合并两个局部变量本身。callee 中 `item = NULL` 不会重新绑定 caller 的 p；callee 通过 `*pp` 写入才可能改变被指向的 slot，需另有唯一指向证据。

## 4. 拟议的最小中间记录

以下是字段设计说明，不是已实现 schema 或新模型提示词。

| 记录 | 必填信息 |
| --- | --- |
| SourceEvidence | dataset_id、position、源码版本/历史 blob、文件/函数 body hash、spelling/expansion 源范围、构建证据是否完整 |
| CallEdge | caller/callee 声明身份、callsite 精确范围和原文、签名、参数序号与转换、检索来源/selection_tier、直接调用核验结果 |
| ValueVersion | slot_id、上下文、path_id、定义位置、值类别与类型、前一版本/依赖、unknown reason |
| StateEnvironment | 当前点各 slot → 当前 version；独立内存版本；地址逃逸/可能写集合；未验证效果清单 |
| TransferRecord | caller pre、callee entry、实际值映射、已验证转换、ret/out effects、caller post、PASS/REJECT/UNKNOWN 及证据 |
| ConstraintRecord | 不可变原始文本/哈希、B/Δ/传播来源角色、完整 atom 来源、所用 slot/value/memory version、path/call context、极性和语义检查状态 |
| FunctionSummary（后期） | 前提、返回路径集合、return 值、读/写 footprint、别名/逃逸、未覆盖项、源码/构建/分析器版本、重用条件 |

无法将历史约束中的一个符号唯一绑定到源码值版本时，必须保留原文并返回 UNKNOWN，不能猜它对应“最后一次赋值”。历史 `variable_assignments` 的函数签名占位不能当定义。

## 5. 赋值与调用状态的最小规则

1. 简单直接赋值产生新值版本；旧版本及其约束保留在账本中。使用点引用沿该路径可证明到达的当前定义。
2. `q = p` 是当时值复制：q_new 与 p_current 建立关系；之后 p 更新不改 q。除非另有证据，不能据此证明内存存活、对象内容相同或没有别名写入。
3. 不在首轮推断 `malloc`、`alloc_skb`、`kstrdup` 等函数名的分配/非空语义。未知返回值产生单独结果版本；不能默认非 NULL。精确库模型若以后引入，必须单独列依据、范围和验收。
4. `p = call()` 需要区分表达式返回值绑定与调用的其他效果。识别“p 获得新版本”可以局部 PASS，而全调用传播在效果未覆盖时仍是 UNKNOWN。
5. `init(&p)` 要把实参绑定到 p 的 slot 地址。只有唯一 local slot、直接可见间接写入、完整受限函数体和效果范围可验证时，才提交 p 的新版本；不能仅看到 `**` 或 `&` 就断言已修改。
6. 未知调用/别名写入不得假定保持原值。记录可能失效的当前状态，产生未知后状态或直接停止该项传播。若连可能写集合都无法可靠界定，不宣称其他内存保持；原历史约束仍绑定旧版本，不删除原 B/Δ，也不让未知值参与过滤证明。
7. volatile/原子/共享可变状态不能用普通 SSA 局部读取替代并发语义。READ_ONCE/WRITE_ONCE 等暂为 UNKNOWN，除非以后专门提供构建和内存模型。

## 6. 路径传播：条件合并必须限定在同一路径/上下文

拟议的单条已验证调用路径关系为：

`CallerPre(path_a, point_before_call)` + `ArgumentTransfer(edge, current_versions)` + `CalleeEntry` + `CalleePath(path_b)`。

只有处于同一个兼容调用/路径组合中的条件才合取。不同路径以不同记录保存；若需要逻辑表示，则为带守卫的备选关系，不能无条件将两个分支都相与。不能把旧“各帧各自可满足”当成同一全局状态存在的证明。

callee 提前 return 的约束仅刻画相应返回路径。它能排除 callee 内更后的 Sink 路径，却不意味着 caller 自动退出；callee 正常返回后，caller 可能继续执行。调用方已有 NULL 假设也只有绑定到相同、未被改变的值版本时才能传播到目标。

首期建议无环、无递归；每个样本最多 3 层已验证调用上下文、8 个路径状态（均为待批准的资源上限）。超过预算输出明确 UNKNOWN，不静默截断成成功。这与现有 Harness 检索 5 次扩展决策上限是不同的计数，不改原上限。

## 7. 保留 B+Δ，又不能把旧状态断言作用到新状态

原始 B、Δ、Final 文本、哈希及 E02/E03 同帧检查均保持。新增传播关系先作为**独立 sidecar IR** 记录，不回写模型响应，不自动重命名历史 Python，不为得到 SAT 删除冲突。

跨帧源码值需要命名空间，但原 E02 的字面保留契约不自动证明改名正确。因此：

- R01–R04 只输出传播证据与诊断，不把版本符号强塞回旧 U02/U06/U10，也不生成新求解脚本。
- R05 首先仍是离线 IR 组合。如果将来授权导出跨帧约束，需要对**每条**原断言建立完整、可复核的 source/value binding 与一一映射；原字节保留，导出为另一个有 provenance 的派生产物。
- 同帧原 B+Δ 结构检查继续由未改 E02/E03 执行；派生版本表示还需独立检查所有原断言的映射完整性、值版本、类型和路径守卫。不得把 E02 的 raw PASS 宣称成派生表示已获验证。
- 某原 SMT 名称混合多个源码状态时不存在可靠的一一映射，应 REJECT/UNKNOWN，不通过“修正命名”强行消除原矛盾。
- 引入派生导出、真实模型输入或主 engine 接入，都属于未来独立变更和验收范围，不是本阶段授权的功能。

## 8. 函数摘要与原架构的关系

首几轮不做结果摘要缓存。后期即使恢复论文中的 Function Call Memory，也必须以源码/构建/分析器版本、完整支持的前提、参数类型与别名形态、路径和效果覆盖为键；先采用严格相同前提匹配，不推断“看起来类似”的可重用性。摘要实例化时生成新的调用/局部 slot 和值版本，不串用两个 callsite 的符号。

保持单 Agent。get_alert_context/lookup_function_source 只供源码检索，均由调用者绑定原 dataset_id 和 position，遇歧义/缺定义停止该边。传播检查属于独立确定性侧层，LLM 可解释或提出候选，不能自行批准身份/效果。原作者 Prompt 继续原样保存；本阶段没有新增适配 Prompt。

如果未来原 Prompt 的输出无法携带足够来源，先把该输出判为 UNKNOWN；需要新接口/适配模板时另立版本、单独对照，不偷偷覆盖作者模板。
